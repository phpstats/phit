Verification

phit’s numerical results are checked against reference implementations on shared inputs. This page lists the routine checks, the shared metric, and the record for each model or API. Running the checks needs the build environment described in Development.

Routine checks

From the repository root:

cargo fmt --all --check
cargo test --workspace --locked
cargo build -p phit --locked
# macOS; use libphit.so on Linux
export STATS_EXTENSION="$PWD/target/debug/libphit.dylib"
php -n -d "extension=$STATS_EXTENSION" -m
php -n -d "extension=$STATS_EXTENSION" tests/ols.php
php -n -d "extension=$STATS_EXTENSION" tests/logistic.php
php -n -d "extension=$STATS_EXTENSION" examples/ols.php
php -n -d "extension=$STATS_EXTENSION" examples/logistic.php
  • cargo test checks the Rust engine. The extension crate has no Rust test harness, so binding changes also need the PHP integration tests.
  • scripts/check runs the full offline suite: clippy, the Rust tests, a release build, the stub check, the PHP test suites, and the runnable examples in examples/.
  • For a release build, build with --release and run the PHP scripts against target/release.
  • CI runs the suite on Linux and macOS. The packaging workflow runs it on Linux x86_64 and aarch64 with PHP 8.3, 8.4, and 8.5, including a PHP-FPM request.
  • The Rust and PHP tests read saved fixtures. R, Python, and their packages are needed only to regenerate fixtures or run the live comparisons.

Shared metric

Unless a record states otherwise, each numerical quantity passes when

\[|\text{phit} - \text{reference}| \le a + r\,|\text{reference}|,\]

with an absolute part \(a\) for values near zero and a relative part \(r\) for larger values. Sample accounting (retained and dropped rows, group labels and order) must match exactly.

  • The absolute part means the tolerance does not establish relative accuracy for p-values far smaller than \(a\). Extreme tails need focused tests.
  • A pass shows agreement on the tested inputs. It is not a proof of correctness for every floating-point input.
  • Where phit deliberately differs from a reference, the difference is tested explicitly and listed in the record.

OLS fixtures and coverage

tests/fixtures/ols-r.json holds results from base R 4.6.1 lm(), summary(), confint(), and logLik(), regenerated with Rscript tests/generate-fixtures.R. The simulated rows in docs/data/housing.csv are shared by the PHP example, the notebooks, and the one- and two-predictor fits. To regenerate them, run Rscript tests/generate-learning-data.R first (it fixes its RNG and seed), then the fixtures, the three-way report, and the notebooks.

The comparisons cover coefficients, covariance, fitted values, residuals, standard errors, t statistics, p-values, confidence intervals, RSS, residual variance, sigma, R-squared, adjusted R-squared, likelihood, and residual df. Perfect fits compare coefficients, predictions, residuals, and standard errors only, since their t, p, R-squared, and likelihood are unstable. R’s undefined quantities are stored as JSON null.

The binomial mixed-model verification also checks normal quadrature moments, tiny tail weights, the reduction to an ordinary GLM at zero variance, predictor units, and count limits. PHP intercept and offset contracts

tests/intercept.php checks all seven matrix fitters with predictors-only inputs against the same complete design passed with intercept: false. The results must be identical, including covariance, likelihood, group effects, row accounting, and diagnostics. No-intercept and intercept-only models are tested separately. Automatic intercept insertion never changes a random-effects design.

Poisson exposure checks compute the intercept-only weighted MLE, its standard error, the likelihood, and fitted counts independently, with absolute tolerances of 1e-10 for the coefficient and standard error and 1e-9 for the likelihood and counts. Rescaling the exposure must shift only the intercept and leave the fitted counts unchanged. Weighted and offset fits with the default intercept also match stored R fixtures at 1e-7 + 1e-6. Missing offsets follow the same deletion, warning, and strict-rejection rules as other inputs.

Distributions, descriptive statistics, sampling, and draws

  • tests/distributions.php makes 8,618 reference comparisons, uses 25 independent mpmath adjudications, and checks 43 documented boundary differences. See the distribution record.
  • tests/descriptive.php adds 145 R quantities, type-7 scalar and batch identities, missing-value policies, pairwise alignment, weight definitions, and overflow errors. Descriptive statistics documents undefined correlation separately from numerical failure.
  • tests/smoothing.php compares 15,639 density, bandwidth, interpolation, and ECDF quantities with R at relative 1e-12.
  • Seeded sampling uses 25 independently generated Python and R cases: 2,000 Rust engine and quantile values and 1,616 PHP transformed values, plus repeatability, prefix, state-isolation, domain, and moment checks.
  • crates/stats-core/tests/draws.rs and tests/draws.php use 25 independent 80-digit Python Decimal cases, including covariance-map identities, affine round trips, and log determinants. See Draw numerics.

To refresh the PHP distribution evidence without changing the reference values:

PHP=/path/to/matching/php .context/v02/python/bin/python docs/verifications/compare_distributions.py --stored-references
python3 scripts/reference-manifest.py
python3 scripts/distribution-docs.py

Contributor notes

  • When changing an estimator or inference calculation, add a case that distinguishes the intended behavior from the old behavior.
  • Compare against R where its conventions match phit’s, and test deliberate differences explicitly.
  • Keep fixture inputs, generator, and expected outputs together, and inspect regenerated fixture diffs. Do not relax a tolerance to hide a discrepancy.
  • When reporting verification, name the Rust and PHP checks that ran and the platform.
  • For documentation-only changes, check links, commands, and claims against the source. Rerun numerical tests when behavior or implementation changes.
  • Benchmarks run separately from the test suite. Check their numerical agreement before reporting timings.
